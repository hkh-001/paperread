# 检索稳定性改进与验证

日期：2026-10-23。本轮不调用任何模型 API，不运行题集评测，旧实验结果保持不变。

## 改了什么

- 维基请求串行执行，请求起点至少间隔 1.5 秒（同一 WikiStore 实例）。
- 429 / 408 / 5xx、网络异常、无效 JSON，以及 MediaWiki 的 ratelimited / maxlag / readonly 可重试。403 等其他错误直接失败，不盲目重试。
- 优先尊重 Retry-After 的秒数或 HTTP 日期，同时采取 2、4、8 秒量级的指数退避加少量随机等待；默认最多 3 次重试，即最多 4 次 HTTP 尝试。
- 每条 API 查询默认有 90 秒预算，在等待和发起请求前检查剩余时间，网络 timeout 不超过剩余预算。等待要求超过预算时直接记录失败，不提前请求；限流冷却状态保留给下一条查询。
- 此预算不是整个模型动作或整道题的上限：一次 Search 可能先查标题，再查候选列表，各自有查询预算。urllib timeout 控制网络阻塞，不是操作系统级强制终止计时器。
- 共享缓存位于 cache/wiki，默认新鲜期 7 天。每轮先查自己的固定快照，再查共享缓存，再请求网络；共享命中复制到本轮快照，保留原始获取时间。
- 失败不会缓存成成功；过期或损坏的共享缓存会重新请求；已存在的本轮快照不因 TTL 过期而自动替换。
- 事件写入 retrieval.jsonl；每题 trace 增加 retrieval_events；报告增加 HTTP 尝试、重试、429、缓存命中与等待统计。
- 检索模块哈希与各参数写入 manifest，修改后必须新建运行目录，不与旧版续跑混合。

## 真实请求重放

选取前两轮工具失败轨迹中出现的三个实际搜索参数，使用改进后的工具重新查询：

| 查询 | 请求是否正常完成 | 返回类型 |
| --- | --- | --- |
| Stuart Bird film director | 是 | 没有精确实体，返回候选标题 |
| Stuart Baird filmography | 是 | 没有精确实体，返回候选标题 |
| Wendy Schaal | 是 | 返回实体页面文本 |

首次会话共 5 次 HTTP 尝试（前两个搜索各需两次请求），没有遇到 429；累计节流等待约 2.124 秒。第二个会话使用不同运行目录，强制禁止网络请求，再查询同一批参数：3/3 正常，5 次共享缓存命中，0 次网络请求。

真实请求这次没有触发限流，因此“429 后按要求重试”由自动测试证明；真实重放只能证明本次三个请求可用、共享缓存机制有效，不能证明今后不会再限流，也不能把成功全部归因于改进。

机器可读结果见 [validation.json](validation.json)，原始事件见 [首次会话](cold/retrieval.jsonl) 与 [缓存会话](warm/retrieval.jsonl)。大段维基响应保存在本机 runs/11-retrieval-stability-validation/*/wiki_cache 中，没有批量上传到 Git。

## 如何再次验证

在复现实验目录中执行（输出目录应为新目录）：

```bash
python3 -m unittest discover -s tests -v
python3 validate_retrieval.py --out runs/retrieval-check-next
```

之后若要运行模型调试，原 run 命令仍可使用，新的检索默认值自动生效。预留的 eval50 未运行。

## 使用限制与来源

一个进程内的 WikiStore 串行节流；不要把它理解为多个并发进程之间的全局限流器。为了公平比较，记录缓存策略与获取时间，并保留同一轮快照。跨运行共享缓存会改变实际网络请求数，不能把缓存带来的速度变化直接当成模型推理速度提升。

实现依据：[MediaWiki API 使用建议](https://www.mediawiki.org/wiki/API:Etiquette)、[HTTP Retry-After 规范](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)。没有更改模型提示词、知识内容或评分标准。
